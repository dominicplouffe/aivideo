# DemoRiff

**Studio-grade product demos from a rough screen recording.**

DemoRiff turns one raw screen recording into a directed demo video and a
step-by-step written guide with screenshots taken from the footage — cut by
editing the transcript, so deleting a word removes those milliseconds of
video.

This repository contains the complete public marketing site and the full
application, built as a single Next.js project.

**What works end to end today:** record or import → transcribe → edit as
text → render an MP4 with FFmpeg → publish it to a share page and an embed.
Interactive tours and social cuts are designed and not built; the export
dialog says so rather than offering them. Anything the app cannot measure,
it declines to display.

## Running it

### The marketing site, with no configuration

```bash
npm install
npm run dev     # http://localhost:3000
```

The public site is fully browsable this way. So is `/app`, but it will be
empty: without a database there is no workspace to be in, and every screen
renders the empty state that says so.

That last part is newer than it sounds. `/app` used to serve a seeded
workspace — Meridian, seven members, eight projects with view counts — and
the same fallback fired whenever a real query came back empty, not only when
the database was missing. So an account created a minute earlier was shown
another company's projects, greeted by another person's name, and given a
retention curve generated by a PRNG, all beside its own genuine zeros with
nothing on screen to tell the two apart. Nothing that renders can reach the
seeded data any more, and `lib/no-fixtures.test.ts` fails if anything tries.

### The application, with a database

This is what turns on accounts, the durable queue, metering, the audit log
and everything else that needs to persist.

```bash
createdb demoriff
cp .env.example .env.local        # DATABASE_URL is the line that matters

npm run db:migrate
npm run dev
```

Then **create your own workspace at `/signup`**. Press any of the three
buttons: without WorkOS credentials a development identity provider stands in
for one, asserts the address you typed and hands the browser straight back,
so the whole path — signed state, nonce cookie, callback, provisioning,
session — runs exactly as it does in production. You get what you would
expect on day one: no projects, no views, no languages, ten free video
minutes.

There is no password field, and that is deliberate rather than unfinished.
Passwords live with the identity provider; this application never sees one.
The email box below the buttons is a development convenience that looks up an
existing member and is refused outright in production.

A workspace is created the first time somebody signs in whose address has no
member row — and **only** when their provider says the address is verified.
That gate is the whole reason signup can run in production at all: the route
it replaced took an address and believed it, which is why it answered 501
there. A verified Google account at a company's domain still never joins that
company's existing workspace; it gets its own. Proving you can receive mail
at a domain is not the same claim as that company agreeing to let you in.

`npm run db:seed` writes a demo workspace if you want one to look at. It is
for demos and for the test suite; nothing in the app falls back to it.

Signing in as members with different roles is the quickest way to see the
permission model: a reviewer can approve an agent run and cannot start one, a
creator the reverse. Roles are enforced in the data layer, so the API refuses
too — not just the UI.

### The rest

```bash
npm run build           # production build (also builds the embed script)
npm run start           # serve the production build
npm run typecheck       # tsc --noEmit
npm test                # 566 unit tests, with DATABASE_URL set
npm run test:all        # end-to-end: signup → publish → analytics (see below)
npm run worker          # render + webhook + audit-stream worker (needs ffmpeg)
npm run build:extension # the Chromium capture extension, into extension/dist
npm run db:studio       # browse the database
```

**Run the end-to-end suite** with `npm run test:all`. It migrates, starts the
server and the worker, and drives the whole loop against a workspace it
creates itself through the real signup route — record, transcribe, render,
publish, watch, and then checks that every figure on the analytics page
matches a direct SQL count. It needs `ffmpeg` and `ffprobe`, because it
asserts on a real encoded file rather than on the fact that a job said it
finished, and a Chromium, because one of the tests sweeps every page in a
real browser for hydration errors and overflow. `npx playwright install
chromium` provides one; `CHROMIUM_PATH` points at a browser you already
have. The script refuses to start without either, rather than letting that
test skip itself and reporting the run as a pass.

It runs its four files one at a time. They share one server, one database
and one worker, so running them at once is the suite competing with itself
rather than a test of anything — it cost a run to a request that never got a
connection.

**Run the worker to export anything.** Rendering happens in a separate
process, so `npm run worker` has to be running alongside `npm run dev` for
the export dialog to produce a file. It needs `ffmpeg` and `ffprobe` on the
PATH. If you forget, the dialog says so and names the command rather than
spinning.

The extension loads into Chromium via `chrome://extensions` → Developer mode
→ Load unpacked → `extension/dist`.

### Signing in for real

```bash
WORKOS_API_KEY=...      # both are required; there is no other way in
WORKOS_CLIENT_ID=...
```

Register `<NEXT_PUBLIC_SITE_URL>/api/auth/authkit/callback` as the redirect
URI in the WorkOS dashboard, and switch on whichever methods you want —
Google, Microsoft, passwords, magic links. Enterprise SAML rides the same
integration: a workspace's `sso_connections` row records the WorkOS
organization, and a login carrying that organization lands in that workspace
and nowhere else.

### Turning on a real vendor

Provider selection is per capability: set one key and that one capability
becomes real, with the rest staying on deterministic mocks.

```bash
DEEPGRAM_API_KEY=...     # real transcription — the one the editor rests on
ANTHROPIC_API_KEY=...    # the Riff assistant, translation, frame masking
ELEVENLABS_API_KEY=...   # synthesized narration (also needs DEMORIFF_WORKSPACE_ID)
```

`GET /api/providers` reports what each capability resolved to and what is
missing where it did not, and the Studio says on screen when a transcript
came from the mock rather than a microphone.

`.env.example` documents every variable, each with a note on what breaks
without it. None is required for either path above.

> `npm audit` reports four moderate advisories, all inside `drizzle-kit`'s
> deprecated `@esbuild-kit/*` loader. It is a devDependency used to generate
> and apply migrations; it is not in the dependency tree the application
> ships.

## Architecture

```
app/
  (marketing)/    Public site — shares one header/footer shell
  (app)/app/      Authenticated workspace — sidebar shell + ⌘K palette
  (auth)/         Sign-in and sign-up
  (public)/d/     Public share pages (no app chrome)
  api/            Route handlers
components/
  ui/             Primitives: Button, Icon (80 glyphs), Card, Reveal…
  brand/          Logo and wordmark
  marketing/      Site header/footer, hero canvas, previews, prose renderer
  app/            App shell, recorder, studio, editors, analytics
  app/studio/     Timeline model, canvas, transcript, inspector, export
lib/
  providers/      Provider interfaces + deterministic mock implementations
  *-content.ts    Typed content models (product, solutions, compare, blog,
                  academy, docs, legal, changelog, customers)
  data.ts         The data access layer. Every workspace read goes through
                  here, every read is authorized, and nothing is invented —
                  empty is a real answer and the pages render it
  app-data.ts     Types only. The seeded workspace it used to carry now
                  lives in lib/db/scripts/fixtures.ts, which nothing that
                  renders is allowed to import
```

### Two decisions worth knowing about

**The edited-timeline model.** `components/app/studio/types.ts` flattens a
project into a single list of words, each carrying a frame range. Removing
fillers or deleting a scene genuinely shortens the finished duration, which is
what the header, the timeline, the export dialog and the billing figure all
read from. Nothing is faked with a separate "duration" field.

**The provider boundary.** No component or route handler talks to a vendor SDK.
Transcription, synthesis, translation, camera direction, masking and rendering
are six interfaces in `lib/providers/types.ts`. Wiring a real vendor means
writing one adapter and returning it from `getProviders()`; everything above
that line is untouched.

## Design system

Defined entirely as tokens in `app/globals.css`, in a dark and a light palette.
Colour utilities are mapped through Tailwind v4's `@theme inline`, so `bg-ink-900`
resolves against whichever palette is in force where the element sits. Components
never hardcode a hex value.

- **Appearance** — light, dark, or follow the system, chosen under Settings →
  General and stored per device in `localStorage`. A script in the root layout
  applies it before first paint. The marketing site and public share pages pin
  themselves to dark with `data-theme="dark"`, because their artwork is drawn
  for it.
- **Surfaces** — a nine-step ink ramp from `ink-1000` (the page) to `ink-500`;
  the steps keep their meaning in both palettes
- **Brand** — one signature gradient: iris → violet → cyan
- **Type** — Inter for UI, JetBrains Mono for labels and code
- **Motion** — a shared `IntersectionObserver` drives every scroll reveal, and
  all animation is disabled under `prefers-reduced-motion`
- **Icons** — 80 hand-drawn glyphs in one component, no icon dependency

Production dependencies: `next`, `react`, `react-dom`. That is the whole list.
